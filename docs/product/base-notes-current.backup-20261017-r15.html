H1BLE OTA 升级方案

本文档记录 Base Notes 配套设备（CH585）OTA 升级的方案选型与执行细节，重点是上行通道的可靠性。所有结论以实测数据为准，定稿后同步更新 docs/0803 计划。

H2背景

  • 固件包 64~256KB，单次升级窗口约 3~8 分钟；
  • 设备侧资源受限，重传缓冲仅 4KB，无法做完整窗口重传；
  • 现网 notify 通道在弱信号环境下丢包率约 2%，且无应用层确认。

H2现状：notify 上行

设备通过 notify 将升级进度与校验结果推送给上位机，上位机发送 start 命令后进入等待。问题在于 notify 不保证送达，设备侧重发间隔与上位机 read 的时机都缺少约定，长尾进度经常丢一帧。

notify 是「发了不管」；indicate 有应用层 ACK，适合做控制通道，代价是吞吐略低。

H2候选方案

  1. 继续 notify + 应用层序号校验，丢帧由上位机按序号补问；
  2. 上行切 indicate，牺牲约 15% 吞吐换取可靠性；
  3. start 之后固定窗口 read，把主动权收回上位机。

H2下一步

  • 整理三种方案的吞吐 / 延迟实测数据
  • 与固件侧确认 indicate MTU 与连接间隔
  • 定稿后更新 docs/0803 计划并同步 README
