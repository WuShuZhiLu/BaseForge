# BaseForge PM 完善：对齐 PingCode 的「编辑器 + 文档 + Git」融合方案

以 PingCode 为标杆：工作项正文直接用完整版富文本编辑器（新建表单与详情抽屉一致），文档关联成体系，Git 双向同步真正自动、失败可见。

## 已核实的现状（决定了改什么）

1. **编辑器**：工作项已用知识库同款 Tiptap 引擎（`PmRichTextEditor`，复用 `getTiptapExtensions()`），但工具栏只有 10 个基础按钮——没有标题、表格、图片、任务列表，这就是与 PingCode 截图的差距。schema 层全部支持，**只差工具栏 UI**。
2. **项目关联**：工作区有未提交的「项目关联多个知识库」完整改动（v142 迁移+后端+前端），未验证未提交。
3. **Git 同步**：双向都依赖手动且失败静默——拉取只更新已关联条目（新 Issue 永远不进来，项目无「订阅仓库」概念）；推送失败只写后端 console；Gitea 不推标签；导入 Issue 一律「任务」不映射 bug。
4. **工作项↔文档**：后端 `pm_item_notes` API 完好，前端「交付文档」区上次提交被移除（你已确认恢复）。

## 实施步骤（每步验证后独立提交）

### 第 1 步：验证并提交现有未提交改动
构建 + smoke 测试验证「项目关联多个知识库」，修复问题后提交 `feat(pm): 项目可关联多个知识库`。

### 第 2 步：工作项编辑器对齐知识库（PingCode 式，你本次强调的重点）
改造 `PmRichTextEditor` 工具栏（引擎不动，纯 UI）：
- 标题（正文/H1–H3 下拉）、任务列表、表格（默认 3×3 可删改）、代码块、高亮、分割线
- 图片：工具栏按钮 + 粘贴插入，走 base64 内嵌（知识库同款兜底链路）；**已知限制**：base64 图推到平台 Issue 不会渲染（GitHub/Gitea 出于安全不渲染 data: URL），本地与知识库内正常
- 新建表单（ItemForm）与详情抽屉（ItemDrawer）共用此编辑器，体验一致

### 第 3 步：恢复工作项「文档」关联区
- 从 git 历史恢复关联面板接回详情抽屉（搜索关联/新建/跳转知识库/解除），后端零改动。

### 第 4 步：Git 双向同步打通（Gitea/GitHub/GitLab）
- **项目订阅仓库**（新迁移 v143，与推送状态列合并为一个迁移）：新表 `pm_project_repos(projectId, gitSourceId, repo, lastImportedIssueNumber)`，`import-issues` 成功时自动记录。
- **增量自动拉新**：`syncProjectFromPlatform` 在更新已关联条目之外，对订阅仓库拉取 Issue，`number > 基线` 的自动导入并推进基线；标签含 bug/defect/缺陷 → `bug` 类型，其余 task。前端已有的「打开项目拉一次 + 每 3 分钟」自动同步即生效，toast 显示「新增 x · 更新 y」。
- **推送失败可见化**：工作项加 `gitSyncState`/`gitSyncError` 列；自动推送重试耗尽写库、成功清空；前端显示「平台同步失败」徽标 + 错误详情 + 「重试推送」按钮（调现有 `POST /pm/git/push`）。
- **推送串行化**：同一工作项自动推送在内存排队，防快速编辑乱序覆盖。
- **拉取保护**：本地有未推送成功修改（`gitSyncState='failed'`）的条目，拉取跳过覆盖并计入 conflicts，前端提示。
- **Gitea 标签推送**：查仓库标签→名称匹配→缺失则创建→PUT label id 数组。

### 第 5 步：版本与提交
- 分批提交（Conventional Commits 中文，对齐现有风格：编辑器、文档恢复、同步各一笔）；全部验证通过后 package.json 升 `1.1.0-preview.1`。

## 验证
- 每步：后端/前端 `npm run build` + 既有 smoke 测试。
- 最终需要你在真实 Gitea 冒烟（我无法替代）：导入 Issue → 平台新建 Issue → 自动拉入 → PM 改标题/描述 → 平台更新 → 断网改一条看失败徽标与重试。验收清单我会在完成后给你。

## 本轮明确不做（避免范围膨胀）
评论富文本化、工作项附件上传（PingCode 的附件 tab）、PingCode 的工作流/评审/基线面板——需要可下轮再加。
